# 交互模型

> 本文是「按返回键会发生什么」的**唯一真源**。代码里的判定与这里不一致时，以这里为准并修代码。
> 适用版本：0.4.0 起。

## 为什么需要一份模型

远控页是一个 SPA：URL 基本不变，页面自己的层级（任务列表 / 会话 / 设置 / 弹层）全靠内部状态。
而 App 是一个原生壳。两者都有「返回」，但**原生不知道页面在哪一层**。

历史问题是把这两套层级混成了一条线：

```
旧实现： if (webView.canGoBack()) goBack() else 退出到入口页
```

这条判据在真机上两种结果都错：

- 用户在**页面内的设置页**里按返回：WebView 历史为空 → 直接退出整个会话。
- 历史里有别的页面（OAuth 授权页、服务器 302 过的 404）：退到那个页面，用户莫名其妙。

根因不是实现写错，是**判据选错了**。「该退哪一层」这个事实只存在于页面 DOM，
`canGoBack` 回答的是「浏览器历史里还有没有上一页」，那是另一个问题。

## 层级

页面层级，从内到外：

| 层 | 判据（页面 DOM） | 返回动作 |
|---|---|---|
| popup | `role=menu/listbox/dialog[data-state=open]` | 原生派发受信任的 Escape |
| sidepane | `[data-mobile-side-pane-overlay=true]` 且未收起 | 点遮罩内的收起按钮 |
| onboarding | `[data-testid=onboarding-page]` | 点「退出引导」 |
| settings | `[data-testid=settings-page]` | 点 `settings-back-button` |
| chat | `[data-mobile-page=chat]` | 点「返回任务首页」 |
| list | `[data-testid=task-new-button]` 可见 | **退到壳子** |
| connect | 「重新连接」文案 + 连接阶段文案，且无会话/列表 | **退到壳子** |
| unknown | 以上都不匹配 | **退到壳子** |

判据全部来自线上 bundle 实测（ZCode 桌面端 `remote/v4` 页面，2026-10-31 抓取），
不是猜的命名。关键的两处细节：

- **列表页用 `task-new-button` 判定，不用 `task-item-*`**：项目全部折叠时任务行数量为 0，
  用任务行判定会把「折叠状态的列表页」误判成未知层。
- **侧栏开合不能用 computed opacity 判定**：遮罩是 class 切换 + 200ms 过渡，
  过渡期间 opacity 仍是旧值（实测打开后 20ms 为 0）。必须用与 class 同步翻转的
  `aria-hidden` / `pointer-events-none`，否则「刚打开抽屉就按返回」会漏判。

## 四层结构（原生侧）

从下往上：

1. **页面**（WebView）。始终活着。壳层打开时**不把它从视图树上摘下**——
   保活链路对可见性极度敏感，页面一旦判定自己不可见就会 suspend transport。
2. **手势层**（`GestureHostLayout`）。左边缘右滑 = 返回，顶部下拉 = 刷新。
3. **壳子面板**（`ShellPanel`）。页面回到最外层时用户退到的地方。
4. **原生覆盖页**（设置 / 日志）。盖住页面，关掉回来草稿还在。

返回键的判定顺序就是这四层的**逆序**：覆盖页 → 壳子面板 → 页面层级 → 再按一次退出。
前三层各由自己的 `BackHandler` 拦截，只有最后一层落到 `RemoteScreen` 的顶层处理器。

## 三个具体问题的答案

### 什么时候退到壳子，什么时候留在页面里

**判据是页面自己报的层级，不是 WebView 历史。** 页面报 `list` / `connect` / `unknown`
（即页面最外层）时退到壳子；报其它任何一层都在页面内消化。

壳子是**从右侧滑入的抽屉**，不是整页替换。理由：远控页的保活、草稿、滚动位置全挂在
同一个 WebView 上，整页替换会让 WebView 失去可见性，后台通知链路随之断掉。

壳子里有四件事：连接状态（当前连的是谁、活着吗）、重新连接、设置、日志、断开。

### 设置页能不能嵌进网页内部

**能，但嵌在页面之上的原生壳层里，不是网页内部。** 两条理由都与正确性有关：

1. 设置里有「后台保活」「检查并更新」「安装未知应用」，这些必须走原生 API
   （前台服务、系统安装器、电池白名单），网页内部做不到。
2. 设置页要跟随页面配色，而配色来自页面本身（`PageThemeStore`）。
   做成叠加层可以直接复用这套主题，不需要在网页里再维护一套色板。

叠加层**不销毁 WebView**：关掉设置回来，草稿与滚动位置都在。
叠加层内部有自己的小栈（设置 → 日志文件 → 单份日志），不跳整个 screen。

### 会话右滑能不能把任务列表切过来

**能，而且这正是它的行为。** 但实现方式是「返回」而不是「手势切页」：

在会话页按返回（系统返回键或系统手势）→ 页面层级是 `chat` → 页面执行
「返回任务首页」→ 落到 `list`。这就是把任务列表拉过来的效果，
和页面左上角那个按钮走的是同一条路径。

为什么不做成一条独立的自绘右滑手势：页面自己已经有一层 88vw 的侧滑面板，
再定义一条从左滑到列表的手势，用户无法预判哪条生效。用「返回」这一个语义
覆盖它就够了——系统手势、返回键、页面内按钮三者结果完全一致。

在其它层按返回不会「切到任务列表」，而是各自退一层：

| 当前层 | 按返回 |
|---|---|
| 弹层 | 关弹层 |
| 侧栏 | 收侧栏 |
| 页面内设置 | 退出设置页 |
| 会话 | **回到任务列表** |
| 任务列表 | 退到壳子 |

### 会话下拉能不能主动触发刷新

**能，而且下拉就是真的刷新。** 唯一的例外是页面正停在浮层/侧栏/设置页里——
那种时候重载会把用户正在编辑的东西一起丢掉，所以不刷。

真正要解决的不是「要不要刷」，而是**从哪儿开始往下拉才算是刷新**。
判定五条同时成立才认，任何一条不成立就完全放行：

1. 页面已经在顶部（`canScrollVertically(-1) == false`）
2. 起手点距屏幕顶部 ≤ 88dp
3. **输入法没有弹起**
4. 纵向位移 > 88dp
5. 纵向位移 > 横向 1.5 倍

条件 1 保证「页面还能往上滚」时下拉一定是滚动——用户在会话中间往下拖是想看前面的内容，
那是滚动，绝不该刷新。

条件 3 是最容易踩到的一种：输入法弹起后页面被压到上半屏，内容被压缩、`scrollY` 变成 0，
用户想回看前面的对话而向下拖。此时条件 1 与 2 全部成立，**只有这一条能挡住它**。
输入法在场时用户的意图是「看内容」，不是「重置页面」。

条件 2 保证从长列表中间往下拖不会被误认。

进度反馈是一条 2dp 的细线，只在手势期间出现，松手即消失。不用 Spinner：
Spinner 转一圈什么都不发生，会让人以为功能坏了。

#### 页面自己有没有下拉刷新

查过线上 bundle（ZCode 桌面端 `remote/v4` 页面，2026-10-31）：

- `ptr` 是 oniguruma 正则库的 `_sharedPtr`，不是 pull-to-refresh
- `touchmove` 只有两处：Radix 的滚动锁定（`document.addEventListener`）、xterm 的终端手势
- `overscroll-contain` 用在局部可滚动列表上（滚动隔离），不触发刷新
- 所有 `refresh` 文案都是按钮（刷新二维码、刷新文件树、刷新 Git 图谱）

**结论：页面没有自己的下拉刷新，不存在两套逻辑打架。**
这条结论只对当时那份 bundle 成立；页面升级后需要重新核对，核对方法见本节末尾。

核对命令（在 bundle 目录下）：

```bash
grep -oi 'pulltorefresh|pull-to-refresh' assets/*.js
grep -o 'addEventListener\(`touchstart`' assets/*.js
```

若出现真正的 pull-to-refresh 实现，正确做法是**撤掉我们这套**，
让页面自己的刷新逻辑生效——两套并存一定会互相打断。

## 手势的判定边界

手势宿主是 `GestureHostLayout`，包在 WebView 外面。必须是父容器：
WebView 自己会 `requestDisallowInterceptTouchEvent(true)`，Compose 层拿不到这个事实，
会出现「页面横向滚动」与「右滑返回」互相抢事件。

| 手势 | 起手条件 | 触发条件 | 放弃条件 |
|---|---|---|---|
| 下拉刷新 | 页面在顶部 + 起手点距屏幕顶部 ≤ 88dp + 输入法未弹起 | 纵向位移 > 88dp 且 > 横向 1.5 倍 | 向上滑、纵向不占优、输入法弹起 |

**边缘滑动返回不做自绘。** 安卓系统手势导航与返回键都会产生 back 事件，
已经由 `RemoteScreen` 的 `BackHandler` 接住并走分层判定。再自绘一套边缘手势
只会与系统返回竞争，而且两边行为不一致时用户无法预判。

`requestDisallowInterceptTouchEvent` 不需要压制：下拉刷新只在页面已经在顶部时才接管，
那时页面本来就没有滚动可抢，WebView 还没来得及请求 disallow。

## 再按一次退出

页面在最外层时，返回不是直接退出，而是：

1. 第一次按 → 展开壳子面板（用户能看到连接状态与设置入口，也算「确认要离开」）。
2. 壳子已在眼前时再按 → 提示「再按一次返回键退出会话」。
3. 2 秒内再按 → 真的退出到入口页。

三条入口（返回键、右滑、壳子）共享同一个时间戳，在两个入口之间交替按也不会被连退两次。

**为什么不是一按就退出**：远控页是用户正在用的工作现场，一次误触就关掉会话、
还要重新粘贴链接，代价远大于多按一次。

## 诊断

`nav.state` 日志行记录页面当时的层级快照：

```
nav.state | reason=back-press {"layer":"settings","ws":"open","wsAgeMs":1200,"bridge":true}
```

用户报「按返回没反应」时，这一行是第一手证据：能直接区分
「脚本没注入」（`script-missing`）、「层级判错」（`layer` 与用户描述不符）、
「页面自己没响应」（层级对但点击无效）。

相关日志：

- `back.route` — 每次返回的判定结果与耗时（`page layer=... took=...ms`）
- `back.shell` — 落到壳子
- `back.exit` — 确认退出
- `refresh.route` — 下拉刷新的判定（`action=none reason=healthy` 之类）
- `nav.state` — 页面层级快照
